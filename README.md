# humanizer_russian

Русский редактор, который не пытается маскировать текст под человека. Он ищет места, где русский действительно звучит неестественно: кальки, неудачное управление и сочетаемость, лишнюю эксплицитность, сбитый порядок слов, канцелярит, регистровые сдвиги и другие проблемы — и умеет оставить в покое то, что уже работает.

Вместо одного встроенного «правильного стиля» здесь есть современная языковая норма, слой живого русского и несколько формализованных редакторских школ. Они могут соглашаться, дополнять друг друга или спорить; источник вывода при этом не теряется.

Цель проекта — сделать текст точнее и естественнее, не меняя его смысл и не подгоняя под детекторы ИИ.

## Зачем ещё один хуманайзер

Многие хуманайзеры работают по внешним признакам: убирают тире, дробят предложения, меняют слова, добавляют разговорность. Иногда после такой обработки текст становится только хуже.

Здесь подход обратный. Сначала сохраняем смысл и нормальный русский. Потом смотрим, что можно убрать, переставить или сказать точнее. Стилистика идёт следом, а не вместо языка.

Русский позволяет многое, чего не любит буквальный перевод с английского: опускать понятное из контекста, менять порядок слов, использовать частицы, неполные предложения, причастия, деепричастия и функциональный повтор. Поэтому хорошая редактура не сводится к таблице «плохих слов».

Например:

> Это не ошибка в расчёте, а ошибка в исходных данных.

Естественнее:

> Это ошибка не в расчёте, а в исходных данных.

Общий кусок можно вынести за противопоставление.

А здесь, наоборот, ничего дополнять не надо:

> — Кого любит Паша? — Машу.

Ответ уже задан вопросом. Полное «Паша любит Машу» прозвучало бы тяжелее.

И повтор тоже не всегда ошибка:

> Никогда. Никогда больше.

Если он работает на смысл и ритм, его нужно оставить.

## Как он думает

У проекта нет единственного «правильного редактора». Сначала действуют смысл и современная языковая норма. Среди допустимых вариантов учитываются живой русский, контекст, голос автора и редакторская задача.

В режиме редколлегии сейчас используются две проектные системы и подключаемые авторские библиотеки и библиотеки источников:

- **Русский язык** — современная норма, пунктуация, синтаксис, управление, причастия и деепричастия, регистр и интерференции, похожие на ошибки РКИ.
- **Живой русский** — контекстная экономия, безопасный эллипсис, информационная структура, функциональный повтор и естественные русские варианты.
- **По системе Норы Галь** — смысловая точность, сочетаемость, голос, регистр, образность, ритм и литературная редактура.
- **По системе Максима Ильяхова и Людмилы Сарычевой** — задача читателя, ясность, доказательность, структура, коммерческий и информационный текст.
- **По системе Корнея Чуковского** — живой язык, канцелярит, штампы, идиоматика, регистр и ритм.
- **По контрастивной модели Линн Виссон** — русско-английская интерференция: управление, вид, залог, отрицание, порядок слов, референция, речевые формулы и ложные друзья.
- **По формализованным принципам Д. Э. Розенталя** — управление, сочетаемость, выбор слова, порядок слов, синтаксис, связность текста, фразеология и литературная правка.
- **По формализованной системе И. Б. Голуб** — лексическая точность, речевая избыточность и недостаточность, грамматика, синтаксис, регистр, образность, благозвучие и редактура.

Редколлегия не имитирует самих авторов. Имена означают оценку по формализованным принципам источника, а не личную рецензию, цитату или одобрение автора.

Если источники согласны, это видно. Если расходятся, сохраняется `SOURCE_CONFLICT`: система не усредняет разные школы и не выбирает самую строгую. Языковая норма при этом не является ещё одним «голосом» — нормативные ограничения действуют поверх редакторских предпочтений.

Точные сведения о текущем составе библиотек, обработанных источниках и количестве правил вынесены в [`PROJECT_STATUS.md`](PROJECT_STATUS.md), чтобы README не устаревал после каждого нового источника.

## Попробовать

У проекта один движок и два способа им пользоваться. Оба режима работают с теми же подключаемыми библиотеками знаний; отдельной второй реализации правил нет.

### Компактный режим

Быстрая проверка, которая начинает с механики и подходит для обычной работы с текстом, предварительной редактуры и CI:

```bash
python3 scripts/check.py text.md
```

По умолчанию видны только высокоточные механические сигналы и настоящие блокирующие ограничения.

Более широкий мягкий проход:

```bash
python3 scripts/check.py --extended text.md
```

Можно явно задать регистр:

```bash
python3 scripts/check.py --register everyday text.md
```

JSON-вывод:

```bash
python3 scripts/check.py --json text.md
```

Текст можно передать и через стандартный ввод:

```bash
printf '%s' 'Это не ошибка в расчёте, а ошибка в исходных данных.' | python3 scripts/check.py
```

Для CI есть `--fail-on-findings`. Коды завершения: `1` — найден `ARTIFACT` или `LANGUAGE_ERROR`; `2` — при `--fail-on-findings` есть другие выбранные замечания; `0` — иначе.

### Режим редколлегии

Глубокий режим для случаев, когда полезно видеть редакторские системы отдельно и сохранять их разногласия:

```bash
python3 scripts/review.py text.md --style neutral
```

JSON-отчёт:

```bash
python3 scripts/review.py text.md --format json
```

Можно задать регистр:

```bash
python3 scripts/review.py text.md --register everyday
```

Или выбрать только нужные библиотеки:

```bash
python3 scripts/review.py text.md --libraries russian,native,gal,ilyakhov,chukovsky,visson,rosenthal,golub
```

Для проекта есть готовые редакционные политики, например:

```bash
python3 scripts/review.py text.md --style rslive_content
```

Источники дополнительных данных подключаются отдельно через `--evidence`; по умолчанию этот слой выключен и не нужен для обычной работы компактного режима или редколлегии. Текущее состояние источников описано в [`PROJECT_STATUS.md`](PROJECT_STATUS.md).

## Что уже умеет проект

### Норма и структура

Есть отдельное русское ядро. Среди проверяемых и моделируемых явлений:

- оформление размеченных заголовков и списков;
- управление и согласование;
- связь деепричастия с семантическим субъектом;
- связь причастного оборота с определяемым словом;
- количественное согласование с сохранением нормативной вариативности;
- пассив, результатив и способы выражения субъекта;
- пунктуационные и синтаксические границы.

Настоящие ошибки класса `NORM` могут становиться блокирующими ограничениями. Книжное или историческое правило не становится нормой только по авторитету источника.

### Живой русский и информационная структура

Проект учитывает то, что часто теряется в буквальном переводе или шаблонной редактуре ИИ:

- безопасный эллипсис;
- факторизацию общего материала в противопоставлении;
- тему и рему;
- функциональную парцелляцию;
- прагматические частицы;
- повтор как смысловой, терминологический или ритмический инструмент;
- причастия и деепричастия как нормальный ресурс русского синтаксиса, а не «сложность, которую надо убрать».

### Кальки и РКИ-интерференция

Есть отдельные независимые от источника правила и контекстные карточки для русского, который формально может быть правильным, но устроен как иностранный.

Например, для английского `break` зафиксирована событийная граница русского `ломаться`: бытовой русский обычно различает признаки неисправности, сам переход и результат, а не переносит `is breaking` напрямую в `ломается`.

РКИ-слой проверяет или моделирует валентность, управление, вид, субъектные отношения, пассив и результатив, связки, порядок слов, референцию и другие зоны интерференции.

Исследование А. В. Величко встроено сюда независимо от источника: оно расширяет профиль **«Русский язык»**, а не создаёт ещё одного фиктивного рецензента. Доступный источник был неполным, поэтому отсутствующие главы прямо помечены как непокрытые и не реконструируются.

### Контрастивная модель Виссон

Виссон используется «в обратную сторону»: английская модель → естественная русская модель → возможная интерференция в русском. Узкие высокоточные случаи вроде `спросить вопрос` или `претендовать, что/будто` могут попадать в компактный режим; вид, залог, отрицание, порядок слов и референция в основном остаются контекстными.

### Накопительные библиотеки

Новые книги одного автора не создают новый голос каждый раз. Они пополняют долгоживущую библиотеку:

- повторяющиеся наблюдения добавляют новые сведения о происхождении правила;
- одинаковые механизмы связываются общим `phenomenon_id`;
- исторические рекомендации проверяются по современной норме;
- контекстные советы остаются `MODEL_ONLY`, если механическая эвристика была бы слишком шумной.

Розенталь и Голуб уже работают именно как накопительные школы: новый источник обогащает существующую систему, а не создаёт ещё одного рецензента.

### Модельные проверки контекстных правил

В репозитории есть отключённый по умолчанию стенд, управляемый манифестами, для правил `MODEL_ONLY`. Кандидат получает только относящиеся к нему карточки правил, а ожидаемый ответ видит отдельная проверяющая модель. Реальные вызовы API не входят в CI и не являются доказательством нормы. Офлайн-контракт проверяет отсутствие утечки ожидаемого ответа и структуру отчётов.

### Внешние источники дополнительных данных

Архитектура умеет прикреплять к явлению отдельные корпусные, словарные, нормативные и синтаксически разобранные данные, не превращая их в голос редколлегии. Этот слой выключен по умолчанию и при сбое не блокирует основной проход: обычные компактный режим и редколлегия не зависят от внешнего API.

## Как устроено знание

Каждый вывод, специфичный для источника, сохраняет собственный `rule_id`, но общие механизмы получают независимый от источника `phenomenon_id`. Благодаря этому компактный режим может убрать дубли одного и того же явления, а редколлегия — показать, какие источники к нему пришли и где они расходятся.

Для новых механических правил действует принцип «сначала точность»: одного положительного примера недостаточно. Нужны естественный отрицательный контроль, пограничный пример, исключения и регрессионный тест. Если для решения нужен смысл, правило остаётся контекстным вместо псевдолингвистического регулярного выражения.

## Книги как сборники правил

Каждую новую книгу сначала читаем и аудируем целиком или явно фиксируем физически доступную границу. Затем выделяем атомарные наблюдения, редакторские операции, исключения, примеры и контрпримеры. Только после этого решаем, что попадёт в механический рабочий контур.

Авторы могут не соглашаться друг с другом. Это нормально. Главное — не терять происхождение вывода и не путать редакторское предпочтение с современной нормой.

## Что здесь важнее всего

Жёсткие ограничения:

**USER_INTENT + SEMANTICS + NORM**

Выбор среди допустимых вариантов:

**AUTHOR > NATIVE_USAGE > EDITING > AI_CALQUE > detector score**

Если текст уже хороший, лучший результат — оставить его в покое.

## Что проект не делает

`humanizer_russian` не определяет авторство текста и не выдаёт «процент ИИ». Он не вставляет ошибки специально, не запрещает нормальные русские конструкции по одному формальному признаку, не считает частотность нормой и не превращает советы из книг в обязательные правила языка.

## Как добавить новую книгу

Для каждого крупного источника используется долгоживущая ветка по фамилии автора. Она сохраняется после слияния и может пополняться следующими книгами того же автора. Это исследовательская ветка, а не отдельный продуктовый режим.

Подробный процесс описан в [`docs/source-integration-runbook.md`](docs/source-integration-runbook.md), [`docs/book-study-framework.md`](docs/book-study-framework.md) и [`libraries/README.md`](libraries/README.md).
