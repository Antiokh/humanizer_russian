# Reusable prompt for deep book study

Ниже — универсальный промпт для глубокого разбора книги по `docs/book-study-framework.md`.

Его задача — получить не обзор и не конспект, а воспроизводимую рабочую базу знаний с полной картой покрытия, provenance, ограничениями, counterexamples и evals.

---

## Полный промпт

```text
У меня есть книга/учебник, который я легально предоставляю тебе для анализа.

Нужно выполнить DEEP BOOK STUDY по этой книге. Не делай обычный конспект и не ограничивайся «главными мыслями».

ЦЕЛЬ

Извлеки из книги максимально полную самостоятельную рабочую систему знаний так, чтобы после завершения study для обычной работы не требовалось постоянно возвращаться к исходному файлу.

При этом НЕ создавай замену самой книге: не воспроизводи длинные фрагменты, не переписывай её последовательно абзац за абзацем и не копируй авторские примеры без необходимости.

Сохраняй все различия, которые могут изменить решение, диагностику, действие или оценку результата.

ВАЖНО

1. Сначала создай source inventory и полную карту оглавления.
2. Затем прочитай источник ПОСЛЕДОВАТЕЛЬНО целиком. Не объявляй книгу разобранной на основе semantic search, случайных snippets или нескольких найденных глав.
3. Отмечай реальный прогресс по каждой главе: UNREAD → READ → EXTRACTED → VERIFIED.
4. Не утверждай полноту, пока каждая глава не получила финальный статус.
5. Если файл читается частями, продолжай по next_read / следующему диапазону до конца источника.
6. Если какая-то часть недоступна или плохо распарсилась, явно пометь gap. Не заполняй его догадками.

ЧТО ИЗВЛЕКАТЬ

Ищи не только явные «правила», но все decision-relevant элементы:

- определения;
- понятия;
- типологии;
- различия между похожими случаями;
- принципы;
- методы;
- процедуры;
- эвристики;
- диагностические признаки;
- причины ошибок;
- ограничения;
- исключения;
- контрпримеры;
- положительные модели;
- отрицательные модели;
- последовательности действий;
- взаимодействия правил;
- конфликты правил;
- приоритеты;
- требования к контексту;
- случаи, где ничего исправлять/менять НЕ надо;
- исторически обусловленные советы;
- genre-specific / audience-specific / translation-specific / domain-specific идеи;
- эмпирические, научные, исторические, правовые или статистические утверждения, которые нуждаются во внешней проверке;
- мета-правила о том, как сам автор предлагает думать, проверять, редактировать, проектировать или принимать решение.

ОСОБО ИЩИ ГРАНИЦЫ

В каждой главе внимательно ищи слова и конструкции, которые меняют силу утверждения:

«обычно», «часто», «иногда», «редко», «почти всегда», «не всегда», «кроме», «если», «только когда», «но», «однако», «может», «нельзя автоматически» и их смысловые аналоги.

Не превращай эвристику в hard rule.

PROVENANCE

Каждый существенный элемент маркируй:

SOURCE_DIRECT — автор формулирует его прямо.
SOURCE_REPEATED — идея устойчиво следует из нескольких мест.
SOURCE_EXAMPLE_ONLY — есть только отдельный пример; обобщение потенциально наше.
PROJECT_DERIVED — операционное правило выведено нами.
PROJECT_REFINED — идея источника ограничена/уточнена современной архитектурой или внешними знаниями.
EXTERNAL_CONFIRMED — позже подтверждена независимым источником.
EXTERNAL_CONTESTED — есть основания считать её спорной/устаревшей.

Не приписывай автору PROJECT_DERIVED или PROJECT_REFINED формулировки.

ДЛЯ КАЖДОГО ATOMIC RULE

Создай карточку:

RULE-ID — короткое название
Source locator
Scope
Basis / provenance
Level: word / phrase / sentence / paragraph / scene / document / corpus
Confidence

Что проверяет
Почему это важно
Семантический/функциональный инвариант — что нельзя потерять при изменении
Trigger / признаки
Диагностические вопросы
Возможные классы исправлений/действий
Когда НЕ применять автоматически
Counterexamples
Do not infer — каких более сильных выводов делать нельзя
Взаимодействия с другими rules
Собственный positive example
Собственный counterexample
Verification — как убедиться, что после применения не стало хуже

Не делай одно большое расплывчатое правило, если книга различает несколько механизмов.
Но и не дроби один механизм искусственно ради количества ID.

CLAIMS AUDIT

Вынеси отдельно утверждения, которые нельзя просто принять на веру:

- нормы языка;
- научные факты;
- статистику;
- психологические причинные связи;
- исторические факты;
- правовые утверждения;
- современные usage claims;
- технические утверждения;
- прогнозы.

Для каждого:

- точный смысл claim;
- locator;
- тип claim;
- насколько он нужен для operational rule;
- verification status;
- нужен ли внешний источник.

Не превращай мнение автора в «доказанный факт» только потому, что оно напечатано в книге.

INTERACTIONS

После разбора глав сделай отдельный cross-book pass.

Найди:

- дубли rules;
- похожие rules с разными границами;
- противоречия;
- prerequisites;
- порядок применения;
- pairs/groups, которые нужно оптимизировать совместно;
- случаи, когда исправление одного дефекта создаёт другой;
- paragraph/document-level эффекты;
- compound failures.

EVALS

Создай оригинальные тестовые случаи. Не копируй авторские примеры.

Для значимого rule желательно иметь:

1. clear failure;
2. clear acceptable/counterexample;
3. tricky context-dependent case;
4. при необходимости compound case.

Проверяй не только способность «исправить плохое», но и способность НЕ испортить хорошее.

Для каждого eval укажи:

- ID;
- prompt/input;
- ожидаемое поведение функционально, а не одной обязательной строкой;
- rules;
- source locators;
- counterexample yes/no;
- что считается ложноположительным срабатыванием;
- что считается потерей смысла.

LOSS AUDIT

После первого полного extraction перечитай каждую главу ещё раз уже против готовой базы.

Для каждой главы ответь:

1. Есть ли различие между похожими случаями, которого нет в базе?
2. Потеряли ли мы исключение или оговорку?
3. Потеряли ли мы положительную модель — что нужно сохранять?
4. Потеряли ли мы причину явления, сохранив только поверхность?
5. Есть ли важный counterexample?
6. Есть ли взаимодействие с другой главой?
7. Есть ли историческое/жанровое ограничение?
8. Есть ли термин или концепция без отдельной карточки?
9. Есть ли важный claim, который мы не вынесли на проверку?
10. Можно ли по нашей базе принять то же решение, которое принял бы внимательный читатель этой главы?

Если нет — доработай extraction.

OVERGENERALIZATION AUDIT

Для каждого rule попробуй намеренно сломать его:

- придумай корректный случай с тем же внешним trigger;
- проверь, не превратился ли advice автора в запрет;
- проверь, не перепутали ли мы корреляцию и причину;
- проверь, не переносим ли translation-specific правило на оригинальный текст;
- проверь, не переносим ли историческую языковую ситуацию на современность;
- проверь, не выдаём ли авторский вкус за нормативную ошибку.

SOURCE / COPYRIGHT POLICY

Если книга охраняется авторским правом:

- не помещай в публичные материалы длинные цитаты;
- не копируй все авторские примеры;
- не делай последовательный близкий рерайт книги;
- используй собственные формулировки и собственные примеры;
- для provenance указывай section/chapter/page/locator;
- короткую цитату используй только если именно формулировка автора существенно важна для анализа.

SOURCE INVENTORY

Зафиксируй:

- author;
- title;
- language;
- filename/format;
- bibliographic metadata;
- confidence in exact edition;
- stable locator strategy;
- exact TOC;
- pagination limitations;
- SHA-256 fingerprint, если технически доступен;
- какие части источника реально прочитаны.

OUTPUT

Собери минимум следующие логические артефакты (можно как отдельные файлы или секции):

1. source.md
2. coverage.md
3. concepts.md
4. rules.md
5. interactions.md
6. claims.md
7. evals.json
8. eval-map.json
9. audit.md

Если study встраивается в существующий проект, дополнительно:

- покажи, какие существующие правила он подтверждает;
- какие уточняет;
- какие опровергает;
- какие новые правила добавляет;
- где возникает конфликт архитектур;
- не изменяй существующие hard constraints без отдельного доказательства.

DEFINITION OF DONE

Не называй работу полной, пока одновременно не выполнено:

- источник последовательно прочитан целиком;
- каждая глава отражена в coverage;
- все decision-relevant distinctions извлечены;
- source и project inference разделены;
- contextual rules имеют counterexamples;
- rule interactions описаны;
- externally verifiable claims вынесены отдельно;
- каждый important rule имеет eval coverage;
- есть compound evals для взаимодействующих правил;
- выполнен loss audit;
- выполнен overgeneralization audit;
- unresolved gaps перечислены честно;
- обычная работа возможна по study без постоянного доступа к книге;
- provenance спорного правила можно восстановить до конкретного места источника.

После выполнения дай финальный отчёт не в стиле «я прочитал книгу», а с числами:

- chapters total / verified;
- concepts extracted;
- atomic rules;
- contextual rules;
- counterexamples;
- claims requiring external verification;
- evals;
- compound evals;
- unresolved gaps;
- какие самые важные идеи могли бы потеряться при обычном кратком конспекте.
```

## Короткий запуск для существующего проекта

Если framework уже лежит в репозитории, достаточно:

```text
Выполни полный deep book study загруженной книги по `docs/book-study-framework.md`.

Не начинай с интеграции книги в действующие rules проекта. Сначала независимо:

1. source inventory;
2. полное sequential reading;
3. coverage map;
4. concepts;
5. atomic rules;
6. counterexamples;
7. interactions;
8. claims audit;
9. original evals;
10. loss audit;
11. overgeneralization audit.

Только после этого сделай отдельный integration pass с текущей архитектурой проекта.

Ничего не считать полным до 100% chapter coverage или явного списка недоступных частей.
```

---

## Почему integration идёт последним

Если сразу читать новую книгу через существующую архитектуру проекта, возникает confirmation bias: модель начинает искать подтверждение уже известных правил и пропускает идеи, для которых ещё нет категории.

Поэтому порядок принципиален:

`BOOK → independent model of the book → audit → integration into project`

а не:

`PROJECT RULES → search the book for support`.

Это одно из главных требований framework.
