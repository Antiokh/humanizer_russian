# Универсальный промпт для глубокого исследования книги

Ниже — универсальный промпт для глубокого разбора книги по `docs/book-study-framework.md`.

Его задача — получить не обзор и не конспект, а воспроизводимую рабочую базу знаний с полной картой покрытия, происхождением выводов, ограничениями, контрпримерами и проверочными сценариями.

---

## Полный промпт

```text
У меня есть книга или учебник, который я легально предоставляю тебе для анализа.

Нужно выполнить ПОЛНОЕ ИССЛЕДОВАНИЕ этой книги. Не делай обычный конспект и не ограничивайся «главными мыслями».

ЦЕЛЬ

Извлеки из книги максимально полную самостоятельную рабочую систему знаний так, чтобы после завершения исследования для обычной работы не требовалось постоянно возвращаться к исходному файлу.

При этом НЕ создавай замену самой книге: не воспроизводи длинные фрагменты, не переписывай её последовательно абзац за абзацем и не копируй авторские примеры без необходимости.

Сохраняй все различия, которые могут изменить решение, диагностику, действие или оценку результата.

ВАЖНО

1. Сначала составь паспорт источника и полную карту оглавления.
2. Затем прочитай источник ПОСЛЕДОВАТЕЛЬНО целиком. Не объявляй книгу разобранной на основе семантического поиска, случайных фрагментов или нескольких найденных глав.
3. Отмечай реальный прогресс по каждой главе: `UNREAD` → `READ` → `EXTRACTED` → `VERIFIED`.
4. Не утверждай полноту, пока каждая глава не получила финальный статус.
5. Если файл читается частями, продолжай по `next_read` или следующему диапазону до конца источника.
6. Если какая-то часть недоступна или плохо разобрана, явно пометь пробел. Не заполняй его догадками.

ЧТО ИЗВЛЕКАТЬ

Ищи не только явные «правила», но все элементы, способные повлиять на решение:

- определения;
- понятия;
- типологии;
- различия между похожими случаями;
- принципы;
- методы;
- процедуры;
- эвристики;
- диагностические признаки;
- причины ошибок;
- ограничения;
- исключения;
- контрпримеры;
- положительные модели;
- отрицательные модели;
- последовательности действий;
- взаимодействия правил;
- конфликты правил;
- приоритеты;
- требования к контексту;
- случаи, где ничего исправлять или менять НЕ надо;
- исторически обусловленные советы;
- идеи, специфичные для жанра, аудитории, перевода или предметной области;
- эмпирические, научные, исторические, правовые или статистические утверждения, которые нуждаются во внешней проверке;
- мета-правила о том, как сам автор предлагает думать, проверять, редактировать, проектировать или принимать решение.

ОСОБО ИЩИ ГРАНИЦЫ

В каждой главе внимательно ищи слова и конструкции, которые меняют силу утверждения:

«обычно», «часто», «иногда», «редко», «почти всегда», «не всегда», «кроме», «если», «только когда», «но», «однако», «может», «нельзя автоматически» и их смысловые аналоги.

Не превращай эвристику в безусловное правило.

ПРОИСХОЖДЕНИЕ ВЫВОДОВ

Каждый существенный элемент маркируй одним из кодов:

`SOURCE_DIRECT` — автор формулирует его прямо.
`SOURCE_REPEATED` — идея устойчиво следует из нескольких мест.
`SOURCE_EXAMPLE_ONLY` — есть только отдельный пример; обобщение потенциально наше.
`PROJECT_DERIVED` — операционное правило выведено проектом.
`PROJECT_REFINED` — идея источника ограничена или уточнена современной архитектурой либо внешними знаниями.
`EXTERNAL_CONFIRMED` — идея дополнительно подтверждена независимым источником.
`EXTERNAL_CONTESTED` — есть основания считать её спорной или устаревшей.

Не приписывай автору формулировки `PROJECT_DERIVED` или `PROJECT_REFINED`.

ДЛЯ КАЖДОГО АТОМАРНОГО ПРАВИЛА

Создай карточку:

`RULE-ID` — короткое название
Указатель на источник
Область действия
Основание и происхождение
Уровень: слово / фраза / предложение / абзац / сцена / документ / корпус
Степень уверенности

Что проверяет
Почему это важно
Семантический или функциональный инвариант — что нельзя потерять при изменении
Признаки, которые должны вызвать проверку
Диагностические вопросы
Возможные классы исправлений или действий
Когда НЕ применять автоматически
Контрпримеры
Каких более сильных выводов из правила делать нельзя
Взаимодействия с другими правилами
Собственный положительный пример
Собственный контрпример
Проверка результата — как убедиться, что после применения не стало хуже

Не делай одно большое расплывчатое правило, если книга различает несколько механизмов.
Но и не дроби один механизм искусственно ради количества идентификаторов.

АУДИТ УТВЕРЖДЕНИЙ

Вынеси отдельно утверждения, которые нельзя просто принять на веру:

- нормы языка;
- научные факты;
- статистику;
- психологические причинные связи;
- исторические факты;
- правовые утверждения;
- утверждения о современном употреблении;
- технические утверждения;
- прогнозы.

Для каждого укажи:

- точный смысл утверждения;
- указатель на источник;
- тип утверждения;
- насколько оно нужно для рабочего правила;
- статус проверки;
- нужен ли внешний источник.

Не превращай мнение автора в «доказанный факт» только потому, что оно напечатано в книге.

ВЗАИМОДЕЙСТВИЯ

После разбора глав сделай отдельный проход по книге целиком.

Найди:

- дубли правил;
- похожие правила с разными границами;
- противоречия;
- предварительные условия;
- порядок применения;
- пары и группы правил, которые нужно оптимизировать совместно;
- случаи, когда исправление одного дефекта создаёт другой;
- эффекты уровня абзаца и документа;
- составные сбои.

ПРОВЕРОЧНЫЕ СЦЕНАРИИ

Создай оригинальные тестовые случаи. Не копируй авторские примеры.

Для значимого правила желательно иметь:

1. очевидный плохой случай;
2. очевидный допустимый случай или контрпример;
3. сложный случай, зависящий от контекста;
4. при необходимости составной случай.

Проверяй не только способность «исправить плохое», но и способность НЕ испортить хорошее.

Для каждого сценария укажи:

- идентификатор;
- запрос или входные данные;
- ожидаемое поведение функционально, а не одной обязательной строкой;
- связанные правила;
- указатели на источник;
- является ли случай контрпримером;
- что считается ложноположительным срабатыванием;
- что считается потерей смысла.

АУДИТ ПОТЕРЬ

После первого полного извлечения перечитай каждую главу ещё раз, уже сверяясь с готовой базой.

Для каждой главы ответь:

1. Есть ли различие между похожими случаями, которого нет в базе?
2. Потеряли ли мы исключение или оговорку?
3. Потеряли ли мы положительную модель — что нужно сохранять?
4. Потеряли ли мы причину явления, сохранив только поверхность?
5. Есть ли важный контрпример?
6. Есть ли взаимодействие с другой главой?
7. Есть ли историческое или жанровое ограничение?
8. Есть ли термин или концепция без отдельной карточки?
9. Есть ли важное утверждение, которое мы не вынесли на проверку?
10. Можно ли по нашей базе принять то же решение, которое принял бы внимательный читатель этой главы?

Если нет — доработай извлечение.

АУДИТ ЧРЕЗМЕРНЫХ ОБОБЩЕНИЙ

Для каждого правила попробуй намеренно сломать его:

- придумай корректный случай с тем же внешним признаком;
- проверь, не превратился ли совет автора в запрет;
- проверь, не перепутали ли мы корреляцию и причину;
- проверь, не переносим ли правило, относящееся только к переводу, на оригинальный текст;
- проверь, не переносим ли историческую языковую ситуацию на современность;
- проверь, не выдаём ли авторский вкус за нормативную ошибку.

ПОЛИТИКА ИСТОЧНИКОВ И АВТОРСКОГО ПРАВА

Если книга охраняется авторским правом:

- не помещай в публичные материалы длинные цитаты;
- не копируй все авторские примеры;
- не делай последовательный близкий пересказ книги;
- используй собственные формулировки и собственные примеры;
- для происхождения вывода указывай раздел, главу, страницу или другой устойчивый указатель;
- короткую цитату используй только если именно формулировка автора существенно важна для анализа.

ПАСПОРТ ИСТОЧНИКА

Зафиксируй:

- автора;
- название;
- язык;
- имя и формат файла;
- библиографические данные;
- степень уверенности в точном издании;
- устойчивую стратегию указателей на источник;
- точное оглавление;
- ограничения пагинации;
- SHA-256 или другой отпечаток файла, если технически доступен;
- какие части источника реально прочитаны.

РЕЗУЛЬТАТ

Собери минимум следующие логические артефакты — как отдельные файлы или разделы:

1. `source.md`
2. `coverage.md`
3. `concepts.md`
4. `rules.md`
5. `interactions.md`
6. `claims.md`
7. `evals.json`
8. `eval-map.json`
9. `audit.md`

Если исследование встраивается в существующий проект, дополнительно:

- покажи, какие существующие правила оно подтверждает;
- какие уточняет;
- какие опровергает;
- какие новые правила добавляет;
- где возникает конфликт архитектур;
- не изменяй существующие жёсткие ограничения без отдельного доказательства.

КРИТЕРИИ ГОТОВНОСТИ

Не называй работу полной, пока одновременно не выполнено:

- источник последовательно прочитан целиком;
- каждая глава отражена в карте покрытия;
- все различия, способные изменить решение, извлечены;
- выводы источника и выводы проекта разделены;
- у контекстных правил есть контрпримеры;
- взаимодействия правил описаны;
- утверждения, требующие внешней проверки, вынесены отдельно;
- каждое важное правило покрыто проверочным сценарием;
- для взаимодействующих правил есть составные сценарии;
- выполнен аудит потерь;
- выполнен аудит чрезмерных обобщений;
- нерешённые пробелы перечислены честно;
- обычная работа возможна по исследованию без постоянного доступа к книге;
- происхождение спорного правила можно восстановить до конкретного места источника.

После выполнения дай финальный отчёт не в стиле «я прочитал книгу», а с числами:

- всего глав / проверено;
- извлечено понятий;
- атомарных правил;
- контекстных правил;
- контрпримеров;
- утверждений, требующих внешней проверки;
- проверочных сценариев;
- составных сценариев;
- нерешённых пробелов;
- какие самые важные идеи могли бы потеряться при обычном кратком конспекте.
```

## Короткий запуск для существующего проекта

Если методика уже лежит в репозитории, достаточно:

```text
Выполни полное исследование загруженной книги по `docs/book-study-framework.md`.

Не начинай с интеграции книги в действующие правила проекта. Сначала независимо:

1. составь паспорт источника;
2. полностью и последовательно прочитай источник;
3. составь карту покрытия;
4. извлеки понятия;
5. извлеки атомарные правила;
6. собери контрпримеры;
7. опиши взаимодействия;
8. проведи аудит утверждений;
9. создай оригинальные проверочные сценарии;
10. проведи аудит потерь;
11. проведи аудит чрезмерных обобщений.

Только после этого сделай отдельный проход по интеграции с текущей архитектурой проекта.

Ничего не считать полным до 100% покрытия глав или явного списка недоступных частей.
```

---

## Почему интеграция идёт последней

Если сразу читать новую книгу через существующую архитектуру проекта, возникает смещение подтверждения: модель начинает искать подтверждение уже известных правил и пропускает идеи, для которых ещё нет категории.

Поэтому порядок принципиален:

`КНИГА → независимая модель книги → аудит → интеграция в проект`

а не:

`ПРАВИЛА ПРОЕКТА → поиск подтверждений в книге`.

Это одно из главных требований методики.
