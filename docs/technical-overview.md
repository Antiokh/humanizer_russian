# Технический обзор humanizer_russian

Этот файл хранит детали, которые нужны разработчику или агенту, но мешают README быть понятным с первого экрана.

## Один движок, два режима

`humanizer_russian` не поддерживает две независимые реализации.

- Компактный режим: `scripts/check.py`.
- Редколлегия: `scripts/review.py`.

Оба режима используют один набор библиотек знаний. Правило не должно иметь отдельную реализацию для компактного режима и редколлегии.

## Базовая иерархия

Жёсткие ограничения:

`USER_INTENT + SEMANTICS + NORM`

Выбор среди допустимых вариантов:

`AUTHOR > NATIVE_USAGE > EDITING > AI_CALQUE > detector score`

Редакторская школа не отменяет норму, живой русский или подтверждённый авторский голос.

## Сначала механика

Сначала выполняется дешёвая воспроизводимая проверка. Контекстная модель подключается только к остаточным случаям, где анализа поверхности недостаточно.

Уровни автоматизации:

- `HARD_GATE` — только действительно надёжное блокирующее нарушение;
- `DEFAULT_MECHANICAL` — высокоточная проверка обычного компактного режима;
- `EXTENDED_SOFT` — полезная, но более шумная механическая эвристика;
- `METRIC_ONLY` — измерение без автоматического вывода;
- `MODEL_ONLY` — семантика, дискурс, жанр, идиома, точка зрения, голос и другие контекстные задачи.

Для нового правила `DEFAULT_MECHANICAL` обязательны положительный пример, естественный отрицательный контроль, пограничный пример и детерминированный регрессионный тест.

## Библиотеки знаний

Каждый источник подключается через отдельную библиотеку:

```text
libraries/<id>/library.json
reviewers/<reviewer_id>.json
scripts/lint_<source>.py
```

Манифест хранит идентичность библиотеки, пространство имён источника, рецензента, адаптер и путь к линтеру. Большое исследование книги в манифест не копируется.

Для новых библиотек предпочтителен адаптер `review_v1`. Старый линтер ядра подключён через адаптер совместимости.

## Нормализованная находка

Правило конкретного источника сохраняет собственный `rule_id`, например `GAL-KANZ-VERB`. Одновременно находка получает независимый от источника `phenomenon_id`, например `editing.action_hidden_in_nominalization`.

Это позволяет двум книгам описывать одно явление независимо друг от друга.

Нормализованная находка содержит как минимум:

```text
rule_id
phenomenon_id
library_id
source_namespace
reviewer_id
project_class
automation_level
verdict
line / excerpt
reason
operation
confidence
```

## Компактный режим

Обычный запуск:

```bash
python3 scripts/check.py text.md
python3 scripts/check.py --json text.md
```

По умолчанию выводятся только `HARD_GATE` и `DEFAULT_MECHANICAL`. Мягкие механические эвристики доступны через:

```bash
python3 scripts/check.py --extended text.md
```

Компактный режим не должен симулировать редколлегию или загружать полное исследование источника.

## Редколлегия

Запуск:

```bash
python3 scripts/review.py text.md --style neutral
python3 scripts/review.py text.md --style rslive_content --format json
```

`scripts/editorial_board.py` группирует находки по явлениям и сохраняет мнения рецензентов. Текущий контракт предусматривает, в частности:

- `CONSENSUS`;
- `MAJORITY`;
- `SOURCE_CONFLICT`;
- `SINGLE_REVIEW` / `REVIEW`;
- `NO_ACTION`.

Конфликт источников считается допустимым результатом. Редакционная политика стиля применяется после сохранения отдельных вердиктов.

Имена реальных авторов в интерфейсе означают «оценка по формализованной системе автора», а не настоящую цитату или личную рецензию.

## Стили

Редакционные политики лежат в `styles/`. Их нельзя зашивать в линтер конкретного источника.

Автор отвечает за собственную систему рекомендаций. Профиль стиля отвечает за то, как конкретный проект разрешает несколько допустимых рекомендаций.

## Долгоживущие авторские ветки

Исследование книги развивается в долгоживущей ветке по фамилии автора: `gal`, `ilyakhov`, `chukovsky` и т. п.

Перед очередным PR ветка подтягивает свежий `main`. При конфликтах архитектурным источником истины остаётся `main`, а авторская ветка сохраняет исследование источника, происхождение, правила и модельные проверки.

После слияния авторская ветка не удаляется.

## Оригиналы книг

Публичный репозиторий не должен содержать полные защищённые тексты книг. Оригиналы можно хранить в отдельном приватном репозитории источника или использовать из текущего контекста агента.

В публичный проект переносятся производные материалы: собственные формулировки правил, указатели на источник, карты источников, тесты, аудиты и сведения о происхождении.

## Основные файлы

- `AGENTS.md` — обязательный архитектурный контракт;
- `SKILL.md` — инструкции компактного рабочего режима;
- `BOARD_SKILL.md` — оркестрация редколлегии;
- `libraries/` — библиотеки знаний;
- `reviewers/` — метаданные рецензентов;
- `styles/` — редакционные политики;
- `scripts/library_runtime.py` — загрузка и нормализация библиотек;
- `scripts/check.py` — точка входа компактного режима;
- `scripts/review.py` — точка входа редколлегии;
- `scripts/editorial_board.py` — слой агрегации и конфликтов;
- `references/` — контекстные знания, подтверждённые источниками;
- `tests/` — детерминированные корпуса.

## Проверки

Минимальный набор перед слиянием:

```bash
python -m compileall -q scripts
python scripts/validate_architecture.py
python scripts/validate_libraries.py
python scripts/lint.py --self-test
python scripts/benchmark_lint.py
python scripts/benchmark_board.py
```

CI также проверяет JSON-схемы и примеры, а также выполняет дымовые тесты профилировщика автора и вывода редколлегии.

Модельные проверки нужны для задач `MODEL_ONLY`, но не заменяют детерминированный сравнительный прогон механических правил.
