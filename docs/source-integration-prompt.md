# Универсальный промпт: интеграция книги в долгоживущую библиотеку знаний

Используйте этот промпт, когда книга или автор уже находятся в контексте разговора.

```text
Продолжи работу с текущей книгой или автором в `Antiokh/humanizer_russian`.

Книга уже находится в контексте этого чата. Не спрашивай заново автора, название или файл, если они уже известны. Если оригинал перестал быть доступен в контексте и происхождение выводов нельзя восстановить, используй подключённый приватный репозиторий источников, если он доступен. Не копируй оригинальную книгу в публичный репозиторий.

Работай в долгоживущей ветке по фамилии автора (`gal`, `ilyakhov`, `chukovsky`, ...). Ветку после слияния не удалять.

Сначала прочитай и соблюдай:
- `AGENTS.md`
- `docs/book-study-framework.md`
- `docs/source-integration-runbook.md`
- `docs/editorial-board-architecture.md`
- `libraries/README.md`

ПОРЯДОК РАБОТЫ

1. АУДИТ ИССЛЕДОВАНИЯ
   Перепроверь существующий разбор книги по методике исследования: покрытие, происхождение выводов, указатели на источник, атомарные правила, положительные операции, ограничения, контрпримеры, взаимодействия, утверждения, аудит потерь, аудит чрезмерных обобщений и сценарии сохранения. Если есть пробелы — сначала дочитай или доразбери книгу.

2. МАТРИЦА ИНТЕГРАЦИИ
   Для всех рабочих правил зафиксируй машинные поля:
   `rule_id`, `source_locator`, `provenance`, `project_class`, `scope`, `semantic_invariant`, `automation_level`, `surface_trigger`, `required_context`, `false_positive_risk`, `positive_case`, `natural_negative_control`, `boundary_case`, `intentional_counterexample`, `existing_overlap`, `native_usage_conflict`, `phenomenon_id`, `planned_module`, `runtime_visibility`.

3. ПРОВЕРКА МЕХАНИЧЕСКОЙ РЕАЛИЗУЕМОСТИ
   Для каждого правила сначала попытайся решить задачу без LLM:
   точное совпадение → регулярное выражение → токенизация → морфология → синтаксический или статистический анализ → только метрика.
   Точность важнее полноты. Не делай псевдолингвистическое регулярное выражение для задачи, которой реально нужен смысл.

4. БИБЛИОТЕКА ИСТОЧНИКА
   Интегрируй автора как отдельную библиотеку знаний, а не как часть единой «редакторской истины».
   Добавь или обнови:
   - отдельный модуль линтера источника;
   - `libraries/<author>/library.json`;
   - `reviewers/<author>.json`;
   - проверки и сценарии источника;
   - производные справочники и данные о происхождении выводов.

   Новые механические модули должны по возможности использовать адаптер `review_v1`.

5. СОХРАНЯТЬ РАЗНОГЛАСИЯ
   Разные авторы могут не соглашаться.
   Не стирай конфликт при слиянии.
   Если разные правила источников описывают один механизм, сохрани разные `rule_id`, но дай им общий нейтральный по отношению к источнику `phenomenon_id`.

6. СНАЧАЛА МЕХАНИЧЕСКАЯ РЕАЛИЗАЦИЯ
   Порядок уровней автоматизации:
   `HARD_GATE` → `DEFAULT_MECHANICAL` → `EXTENDED_SOFT` → `METRIC_ONLY` → `MODEL_ONLY`.

   Для `DEFAULT_MECHANICAL` обязательны:
   - положительный случай;
   - естественный отрицательный контроль;
   - пограничный случай;
   - намеренный контрпример, если применимо;
   - исключения;
   - детерминированная регрессионная проверка.

7. ПОДДЕРЖАТЬ ОБА РЕЖИМА ПРОДУКТА

   COMPACT:
   `python scripts/check.py text.md`

   РЕДАКЦИОННАЯ КОЛЛЕГИЯ:
   `python scripts/review.py text.md --style neutral`

   Compact должен давать короткий объединённый результат.
   Редколлегия должна сохранять происхождение мнений редакторов, консенсус, большинство, конфликт источников и редакционную политику.

8. КОНТЕКСТНЫЙ ОСТАТОК
   Только после механического прохода интегрируй остаток в короткие контекстные справочники и инструкции.
   Не загружай полное исследование книги в обычный runtime и не дублируй промптом то, что уже проверяет код.

9. СОВМЕСТИМОСТЬ С ЖИВЫМ РУССКИМ
   Любое книжное правило класса `EDITING` проверяй против `USER_INTENT + SEMANTICS + NORM` и существующего `NATIVE_USAGE`. Книжная школа не должна уничтожать естественный русский, эллипсис, функциональные повторы, информационную структуру, частицы или авторский голос.

10. ПРОВЕРКА
   До PR запусти:
   `python -m compileall -q scripts`
   `python scripts/validate_architecture.py`
   `python scripts/validate_libraries.py`
   `python scripts/lint.py --self-test`
   `python scripts/benchmark_lint.py`
   `python scripts/benchmark_board.py`
   плюс валидаторы и самотесты конкретного источника.

11. ЖИЗНЕННЫЙ ЦИКЛ ВЕТКИ
   Перед PR аккуратно подтяни свежий `main` в ветку автора, сохранив архитектуру `main`.
   Финальный PR: `<author-branch> -> main`.
   После слияния ветку автора сохранить для следующего цикла.

В финале дай отчёт:
- статус исследования;
- число рабочих правил;
- распределение `HARD_GATE` / `DEFAULT_MECHANICAL` / `EXTENDED_SOFT` / `METRIC_ONLY` / `MODEL_ONLY`;
- новые механические проверки и отрицательные контроли;
- какие правила были сужены или оставлены `MODEL_ONLY`;
- какие `phenomenon_id` пересекаются с другими авторами;
- где обнаружены реальные конфликты источников;
- результаты проверок Compact и редколлегии;
- вырос ли обязательный контекст выполнения;
- что осталось на следующий проход.

Главная формула:
КНИГА → ПРОВЕРЕННОЕ ИССЛЕДОВАНИЕ → МАТРИЦА ИНТЕГРАЦИИ → ПРОВЕРКА МЕХАНИЧЕСКОЙ РЕАЛИЗУЕМОСТИ → БИБЛИОТЕКА ЗНАНИЙ → COMPACT + РЕДКОЛЛЕГИЯ → КОНТЕКСТНЫЙ ОСТАТОК → CI → ВЕТКА АВТОРА → MAIN → СОХРАНИТЬ ВЕТКУ.
```
