# Инструкция по интеграции источников

Эта инструкция описывает интеграцию книги или автора в `humanizer_russian` как **долгоживущей библиотеки знаний**.

Главные принципы:

- `main` — источник архитектуры;
- ветка по фамилии автора (`gal`, `ilyakhov`, `chukovsky`, ...) — долгоживущая линия исследования источника;
- ветку автора после слияния не удалять;
- одна и та же библиотека должна обслуживать два режима продукта: компактный хуманайзер и редколлегию;
- сначала оценить возможность механической проверки, затем оставить контекстный остаток `MODEL_ONLY`;
- разные авторы могут не соглашаться, и этот конфликт надо сохранять.

## Этап 0 — начало

Перед изменениями прочитать:

1. `AGENTS.md`;
2. `docs/book-study-framework.md`;
3. `docs/editorial-board-architecture.md`;
4. `libraries/README.md`;
5. при неполном исследовании — `docs/book-study-prompt.md`.

Если книга уже доступна в текущем чате или контексте, использовать её как первичный источник. Если оригинал недоступен, допускается приватный репозиторий источника. Оригинальные охраняемые книги не копировать в публичный репозиторий.

## Шлюз A — исследование

До интеграции в рабочий контур проверить источник по `book-study-framework`:

- инвентаризацию источника и полноту покрытия;
- последовательное чтение, а не отдельные фрагменты;
- атомарные правила, понятия и полезные операции;
- ограничения и контрпримеры;
- взаимодействия правил;
- происхождение и указатели на источник;
- утверждения, требующие внешней проверки;
- аудит потерь и чрезмерных обобщений;
- проверки сохранения и отсутствия лишних изменений.

Минимальный статус для интеграции — `AUDITED`, предпочтительный — `OPERATIONAL`.

Старые регулярные выражения, жёсткие запреты и старый `SKILL.md` из авторской ветки считаются кандидатами, а не доказательством правильной автоматизации.

## Шлюз B — матрица интеграции

До изменения ядра рабочего контура составить матрицу для всех рабочих правил:

```text
rule_id
source_locator
provenance
project_class
scope
semantic_invariant
automation_level
surface_trigger
required_context
false_positive_risk
positive_case
natural_negative_control
boundary_case
intentional_counterexample
existing_overlap
native_usage_conflict
phenomenon_id
planned_module
runtime_visibility
```

`project_class`:

- `NORM`
- `NATIVE_USAGE`
- `EDITING`
- `AI_CALQUE`
- `AUTHOR`
- `ARTIFACT`

`automation_level`:

- `HARD_GATE`
- `DEFAULT_MECHANICAL`
- `EXTENDED_SOFT`
- `METRIC_ONLY`
- `MODEL_ONLY`

Пространство имён источника (`GAL-*`, `ILY-*`, `CHUK-*`) показывает происхождение, а не строгость.

## Шлюз C — возможность механической проверки

Для каждого правила сначала проверить, можно ли вынести работу из модельной подсказки:

1. точное строковое совпадение;
2. регулярное выражение;
3. токенизация;
4. морфология;
5. синтаксический разбор зависимостей;
6. структурный или статистический сигнал;
7. только метрика;
8. и только затем `MODEL_ONLY`.

Точность важнее полноты. Если естественный отрицательный контроль ломается, правило сужается или остаётся мягким либо `MODEL_ONLY`.

Не писать псевдолингвистическое регулярное выражение для задач, которым реально нужны смысл, референты, тема и рема, идиома, жанр, точка зрения или авторское намерение.

## Шлюз D — библиотека источника

Работа продолжается **в ветке автора**, а не в одноразовой интеграционной ветке.

Перед очередным PR аккуратно подтянуть свежий `main` в авторскую ветку. При конфликтах файлов ядра архитектурный приоритет имеет текущий `main`; знания конкретного источника переносятся поверх него.

Для крупного источника добавить:

```text
scripts/lint_<author>.py        # или другой ясно названный модуль конкретного источника
libraries/<author>/library.json
reviewers/<author>.json
references/...                  # только производные знания и указатели на источник
проверки и тесты конкретного источника
```

Новые библиотеки предпочитают адаптер `review_v1` из `libraries/README.md`.

### `phenomenon_id`

Это независимый от источника идентификатор явления. Если несколько авторов описывают одну проблему, их `rule_id` остаются разными, но `phenomenon_id` должен совпадать там, где механизм действительно один.

Пример:

```text
GAL-...  ┐
ILY-...  ├─> editing.action_hidden_in_nominalization
CHUK-... ┘
```

Так компактный режим может убрать дубли сигнала, а редколлегия — показать независимые мнения.

## Шлюз E — порядок реализации

Обязательный порядок:

1. `HARD_GATE` — только однозначные блокирующие случаи;
2. `DEFAULT_MECHANICAL` — высокая точность + детерминированные отрицательные контроли;
3. `EXTENDED_SOFT` — полезные, но шумные поверхностные эвристики;
4. `METRIC_ONLY` — измерение без ложной нормативности;
5. `MODEL_ONLY` — остаток после механизации.

Для `DEFAULT_MECHANICAL` нужны:

- положительный пример;
- естественный отрицательный контроль;
- пограничный пример;
- контрпример намеренного употребления, если применимо;
- исключения для кода, URL, цитат, диалога и Markdown, если нужны;
- детерминированная регрессия.

Не удалять отрицательный тест ради зелёного CI.

## Шлюз F — два продуктовых режима

Каждая интегрированная библиотека должна быть совместима с обоими режимами.

### Компактный режим

```bash
python scripts/check.py text.md
```

Короткая механическая проверка. Не обязана показывать происхождение каждого редакторского мнения.

### Редколлегия

```bash
python scripts/review.py text.md --style neutral
```

Сохраняет `reviewer_id`, группирует находки по `phenomenon_id`, показывает консенсус, большинство и конфликт и применяет редакционную политику стиля.

Редакционный конфликт — нормальный результат. Не превращать разных авторов в одну «общую истину» при интеграции.

## Шлюз G — остаток `MODEL_ONLY`

Только после механического прохода:

- сделать короткие рабочие справочные материалы;
- не загружать полное исследование книги в обычный рабочий контур;
- подгружать только относящиеся к задаче карточки правил;
- добавить модельные проверки сохранения и отсутствия лишних изменений;
- не дублировать в подсказке то, что уже надёжно проверяет код.

## Совместимость с русским ядром

Любое книжное правило проверить против:

- `USER_INTENT + SEMANTICS + NORM`;
- `NATIVE_USAGE`;
- контекстной экономии и эллипсиса;
- отсутствия немотивированных повторов;
- информационной структуры;
- функциональной парцелляции;
- прагматических частиц;
- профиля автора.

Если совет `EDITING` конфликтует с живым русским, сначала сузить область действия книжного правила.

## Тесты перед PR

Минимум:

```bash
python -m compileall -q scripts
python scripts/validate_architecture.py
python scripts/validate_libraries.py
python scripts/lint.py --self-test
python scripts/benchmark_lint.py
python scripts/benchmark_board.py
```

Плюс самопроверка или валидатор конкретного источника, если он добавлен.

## Жизненный цикл PR и ветки

Финальный PR идёт:

```text
<author-branch> -> main
```

После слияния ветку автора **сохранить**. Следующий цикл:

1. перейти в авторскую ветку;
2. влить свежий `main`;
3. продолжить исследование, правила и тесты;
4. открыть следующий PR из той же ветки.

Таким образом:

- `main` = стабильный собранный движок;
- `gal` / `ilyakhov` / `chukovsky` = непрерывная история исследований конкретных источников.

## Короткая формула

```text
КНИГА / ПРИВАТНЫЙ ИСТОЧНИК
  → ПРОВЕРЕННОЕ ИССЛЕДОВАНИЕ
  → МАТРИЦА ИНТЕГРАЦИИ
  → ОЦЕНКА МЕХАНИЧЕСКОЙ ПРОВЕРЯЕМОСТИ
  → БИБЛИОТЕКА ИСТОЧНИКА + НОРМАЛИЗОВАННЫЕ НАХОДКИ
  → КОМПАКТНЫЙ РЕЖИМ + РЕДКОЛЛЕГИЯ
  → ОСТАТОК MODEL_ONLY
  → ДЕТЕРМИНИРОВАННЫЙ CI
  → АВТОРСКАЯ ВЕТКА → MAIN
  → СОХРАНИТЬ АВТОРСКУЮ ВЕТКУ
```
