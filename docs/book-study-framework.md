# Book Study Framework

Этот framework предназначен для глубокого разбора книг, из которых нужно извлечь рабочую систему идей, правил, методов, исключений и проверок, не превращая репозиторий в копию книги.

Его можно применять к книгам по письму, редактированию, риторике, психологии, менеджменту, дизайну, программированию и другим областям, где важно сохранить не пересказ, а **операционализируемое знание**.

---

## 1. Цель

Framework нужен, чтобы превратить книгу в проверяемую базу знаний, пригодную для дальнейшей работы проекта.

Он должен позволять:

- прочитать источник целиком и не потерять важные части;
- отделить идеи автора от наших выводов;
- сохранить контекст, исключения и ограничения;
- понять не только «что плохо», но и «что делать вместо этого»;
- связать идеи между собой;
- превратить часть знаний в механические проверки там, где это действительно возможно;
- построить evals для контекстных правил;
- не публиковать книгу или близкий пересказ вместо производной системы знаний.

Ключевая последовательность:

> **SOURCE → independent model of the source → audit → operational knowledge → project integration**

а не:

> **PROJECT RULES → search the source for support**

---

## 2. Главный риск: confirmation bias

Если сначала открыть существующий проект и искать в книге подтверждение уже придуманных правил, почти неизбежно получится селективный пересказ.

Поэтому первый проход должен быть максимально независим от текущей архитектуры проекта.

### Правило

Сначала строится собственная модель книги:

- основные идеи;
- категории;
- различия;
- причинные связи;
- положительные рекомендации;
- исключения;
- предостережения;
- критерии качества;
- реальные примеры функций, которые автор считает важными.

И только после этого начинается сопоставление с проектом.

---

## 3. Полное чтение, а не semantic search

Semantic search полезен для навигации и повторной проверки, но недостаточен для первичного разбора книги.

Нельзя считать источник изученным, если работа строилась только на:

- поиске по ключевым словам;
- случайных snippets;
- оглавлении;
- поиске заранее ожидаемых тем;
- нескольких «главных» главах.

### Требование

Нужна карта покрытия книги.

Для каждой главы/раздела хранить статус:

- `UNREAD`
- `READ`
- `EXTRACTED`
- `VERIFIED`

Минимальный Definition of Done для полного разбора: нет `UNREAD` и нет содержательных `READ`, из которых ничего не было извлечено или сознательно отброшено с объяснением.

---

## 4. Что извлекать

Нельзя сводить книгу только к списку запретов.

Из каждого раздела проверять наличие следующих типов знаний.

### 4.1. Concepts

Что за явление описывает автор?

Пример структуры:

```yaml
kind: CONCEPT
name: ...
definition: ...
source_scope: ...
notes: ...
```

### 4.2. Distinctions

Какие вещи автор считает похожими внешне, но разными по сути?

Именно distinctions часто защищают будущий линтер от false positives.

### 4.3. Diagnostics

По каким признакам заметить проблему?

Важно отделять диагностику от автоматического исправления.

### 4.4. Positive recommendations

Что делать вместо плохого варианта?

Это обязательный слой. Если из главы извлечён только анти-паттерн, нужно отдельно проверить, не потерялась ли положительная модель.

### 4.5. Exceptions / guards

Когда похожая конструкция нормальна или полезна?

Для каждого контекстного правила желательно иметь хотя бы один `do not trigger` / counterexample.

### 4.6. Claims

Факты, исторические утверждения, статистика, нормы языка, сведения о современном употреблении.

Такие вещи требуют отдельной проверки по внешним источникам, если источник сам не является современной нормативной базой.

### 4.7. Meta-methods

Как автор сам анализирует текст/проблему?

Иногда метод важнее отдельных примеров.

---

## 5. Provenance

Каждая производная единица знания должна иметь происхождение.

Минимальная схема:

- `SOURCE_DIRECT` — прямо сформулировано источником;
- `SOURCE_REPEATED` — вывод подтверждается несколькими местами;
- `SOURCE_EXAMPLE_ONLY` — идея выведена из примера, но явно не сформулирована;
- `PROJECT_DERIVED` — наш вывод из источника;
- `PROJECT_REFINED` — исходная идея переработана под архитектуру проекта;
- `EXTERNAL_NORM` — подтверждено современной нормативной базой;
- `EXTERNAL_CORPUS` — подтверждено корпусом/эмпирикой;
- `EXTERNAL_RESEARCH` — подтверждено исследованием.

Нельзя маскировать `PROJECT_DERIVED` под прямое утверждение автора.

---

## 6. Scope

У каждой идеи должен быть scope.

Например:

- general prose;
- translation;
- fiction;
- business writing;
- journalism;
- speech;
- historical usage;
- formal register;
- conversational register;
- specific language pair;
- specific audience.

Без scope редакторское наблюдение очень быстро превращается в ложный универсальный запрет.

---

## 7. Source map

Для длинной книги нужен воспроизводимый source map.

Он не обязан содержать длинные цитаты.

Достаточно:

```yaml
rule_id: ...
chapter: ...
section: ...
source_label: ...
derivation: SOURCE_DIRECT
scope: ...
```

Для ebook без стабильной пагинации предпочтительнее внутренний заголовок главы/раздела, а не выдуманный номер страницы.

---

## 8. Независимая модель книги

После первого полного чтения нужно написать отдельный документ, который отвечает:

1. Какую проблему решает автор?
2. Какие ключевые категории вводит?
3. Какие различия для него фундаментальны?
4. Как выглядит хороший результат?
5. Какие методы исправления предлагает?
6. Что нельзя механизировать?
7. Где идеи зависят от эпохи/жанра/регистра?
8. Какие внутренние противоречия есть в книге?
9. Какие идеи повторяются в разных главах?
10. Какие важные вещи плохо укладываются в текущую архитектуру проекта?

Последний вопрос нужен специально против confirmation bias.

---

## 9. Второй проход: operational extraction

После независимой модели начинается второй проход.

Теперь для каждого содержательного узла нужно решить:

- можно ли превратить его в правило;
- это diagnostic или recommendation;
- есть ли положительная операция;
- какие guards нужны;
- можно ли проверить mechanically;
- какие evals нужны;
- какие внешние claims требуют фактчека.

---

## 10. Карточка правила

Для operational rule рекомендуется минимум:

```yaml
id: ...
name: ...
kind: diagnostic | recommendation | guard | norm | heuristic
source: ...
derivation: ...
scope: ...
when: ...
problem: ...
operation: ...
success_test: ...
guards: ...
counterexamples: ...
automation: ...
```

### Обязательное разделение

`when` ≠ `operation`.

Например:

- diagnostic: «есть длинная цепочка отглагольных существительных»;
- operation: «восстановить actor → action → object».

Нельзя делать:

> нашли pattern → удалили слово.

---

## 11. Positive model

Для каждой крупной категории обязательно ответить:

> Что источник считает хорошим текстом/решением?

Если после разбора книги мы знаем только, чего избегать, книга извлечена плохо.

Положительные модели могут быть:

- операции;
- принципы построения;
- критерии результата;
- порядок работы;
- набор вопросов для самопроверки;
- способ выбирать между альтернативами.

---

## 12. Interaction pass

Правила почти никогда не работают независимо.

После извлечения нужно отдельно пройти взаимодействия.

Примеры вопросов:

- одно правило требует убрать повтор, другое — сохранить ритм;
- одно требует конкретики, другое запрещает выдумывать;
- одно требует краткости, другое — оставить необходимую оговорку;
- одно требует разговорности, другое — точного профессионального регистра.

Нужен файл/раздел interactions:

```yaml
rule_a: ...
rule_b: ...
conflict: ...
priority: ...
resolution: ...
```

---

## 13. Automation ladder

Не каждое хорошее редакторское правило можно безопасно превратить в regex.

Рекомендуемые уровни:

### `HARD_GATE`

Только для надёжных технических или нормативных ошибок с очень низким false-positive rate.

### `SOFT_SIGNAL`

Механический сигнал, после которого нужна проверка контекста.

### `EDITING_OPPORTUNITY`

Механически найдено место, где полезно сравнить альтернативу.

### `MODEL_ONLY`

Требует семантики, референтов, голоса, ритма, ситуации или мира текста.

### `METRIC_ONLY`

Число полезно для анализа, но не должно само генерировать warning.

Нельзя повышать правило до `HARD_GATE` только потому, что автор книги считает конструкцию плохой.

---

## 14. Mechanical validation

Для каждого механического правила нужен отдельный набор:

- true positive;
- false positive candidate;
- boundary case;
- intentional use;
- different genre/register;
- code/quote/example exclusion, если применимо.

До корпусной калибровки механические stylistic rules должны оставаться неблокирующими.

---

## 15. Evals для model-only правил

Каждому контекстному правилу нужны оригинальные evals.

Минимум:

1. straightforward problem;
2. counterexample — похожая поверхность, которую нужно оставить;
3. preservation case — исправить одно, не испортив другое;
4. compound case — взаимодействие с другим правилом.

Eval должен проверять функцию, а не дословное совпадение с одним expected output.

---

## 16. Claim audit

Все claims разделить хотя бы на:

- language norm;
- usage frequency;
- historical claim;
- psychology/cognition;
- statistics;
- technology/current practice;
- etymology;
- social/cultural claim.

Для каждого определить:

```yaml
claim: ...
source_status: source_only | externally_verified | disputed | outdated
verification_source: ...
```

Особенно важно: старая редакторская книга не является современной нормативной грамматикой автоматически.

---

## 17. Loss audit

После extraction задать вопрос:

> Что важного из книги исчезло, потому что плохо помещается в формат rules?

Отдельно проверить:

- большие концепции;
- положительные модели;
- длинные рассуждения;
- exceptions;
- эстетические критерии;
- метод мышления автора;
- внутренние противоречия;
- исторический контекст.

---

## 18. Overgeneralization audit

Для каждого правила спросить:

1. Не сделал ли я общий запрет из одного примера?
2. Не потерял ли scope?
3. Не превратил ли translation-specific совет в правило оригинального письма?
4. Не сделал ли историческое предпочтение современной нормой?
5. Есть ли естественный counterexample?
6. Можно ли намеренно использовать конструкцию с хорошим эффектом?

---

## 19. Copyright-safe public layer

Публичный репозиторий должен хранить производное знание, а не замену книги.

Не публиковать:

- полный текст;
- последовательный подробный пересказ каждой главы, который заменяет чтение;
- большие цитаты;
- массив исходных примеров автора;
- extracted source dump.

Можно публиковать:

- оригинально сформулированные правила;
- taxonomy;
- краткие source labels;
- собственные eval-примеры;
- operational workflows;
- source map без длинных цитат;
- анализ интеграции.

---

## 20. Source workspace vs repository

Полезно явно разделить:

### Private/source workspace

- книга;
- extracted text;
- временные notes;
- candidate quotes;
- chapter coverage tables;
- exploratory analysis.

### Public repository

- derived rules;
- source map;
- evals;
- validators;
- integration docs;
- copyright-safe analysis.

---

## 21. Definition of Done

Книга может считаться `OPERATIONAL`, если:

- [ ] все содержательные разделы прочитаны;
- [ ] есть карта покрытия;
- [ ] построена независимая модель книги;
- [ ] извлечены concepts, distinctions, diagnostics и positive recommendations;
- [ ] guards/counterexamples сохранены;
- [ ] provenance указан;
- [ ] scope указан;
- [ ] сделан interaction pass;
- [ ] claims отделены и проверены по необходимости;
- [ ] mechanical rules имеют positive/negative tests;
- [ ] model-only rules имеют evals/counterexamples;
- [ ] сделан loss audit;
- [ ] сделан overgeneralization audit;
- [ ] public output не превращён в замену книги;
- [ ] интеграция в проект выполнена только после независимой модели источника.

---

## 22. Итоговая формула

Хороший разбор книги — это не:

> «нашли 30 плохих слов и добавили regex».

И не:

> «сделали красивый конспект».

Нужна цепочка:

> **прочитать всё → построить независимую модель → извлечь concepts + distinctions + diagnostics + positive operations + guards → проверить взаимодействия и claims → определить automation level → создать negative/positive evals → провести loss/overgeneralization audit → только потом интегрировать в проект**.
