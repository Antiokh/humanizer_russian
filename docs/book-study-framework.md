# Book Study Framework

Этот framework предназначен для глубокого разбора книг, из которых нужно извлечь рабочую систему идей, правил, методов, исключений и проверок, не превращая репозиторий в копию книги.

Он не привязан к Норе Галь или к редактуре русского языка. Его можно применять к книгам по письму, редактированию, риторике, психологии, менеджменту, дизайну, программированию и другим областям, где важно сохранить не пересказ, а **операционализируемое знание**.

---

## 1. Цель

Результат book study должен позволять работать с идеями книги без постоянного доступа к исходнику, но при этом не подменять книгу и не воспроизводить её текст.

Критерий полноты:

> Мы сохранили все различия из источника, которые могут изменить решение, диагностику, действие или оценку результата.

Не нужно сохранять:

- авторскую прозу как таковую;
- длинные цитаты;
- последовательность аргументации слово в слово;
- все примеры источника;
- декоративные истории, если они не меняют правило или его границы.

Нужно сохранять:

- правила;
- методы;
- эвристики;
- определения;
- типологии;
- различия между похожими случаями;
- исключения;
- контрпримеры;
- ограничения применимости;
- причинные объяснения;
- диагностические признаки;
- положительные модели;
- отрицательные модели;
- порядок действий;
- взаимодействие правил;
- исторические или контекстные ограничения;
- утверждения, требующие отдельной проверки;
- случаи, где автор сам оговаривает неопределённость или спорность.

## 2. Основные принципы

### 2.1. Не делать обычный конспект

Обычный конспект отвечает: «О чём эта глава?»

Book study отвечает:

- какое решение меняется после прочтения этой главы;
- какую ошибку она позволяет заметить;
- какие два внешне похожих случая она учит различать;
- что нельзя делать механически;
- где правило перестаёт работать;
- как проверить результат.

### 2.2. Не превращать наблюдение автора в универсальный закон

Каждое утверждение классифицируется по силе и происхождению.

Минимум различать:

- автор явно утверждает;
- автор показывает множеством примеров;
- автор приводит единичный пример;
- это наша интерпретация;
- это современное уточнение;
- это исторически обусловленное утверждение;
- это эмпирическое утверждение, которое надо проверять независимо;
- это норма/правило внешней системы;
- это вкусовая рекомендация.

### 2.3. Хранить отрицательные границы

Для каждого правила важно фиксировать не только «когда применять», но и:

- когда не применять;
- какие похожие случаи допустимы;
- какие случаи автор сам защищает;
- что модель не должна выводить из этого правила.

Это защищает систему от превращения в stop-list.

### 2.4. Хранить взаимодействия

Многие решения нельзя получить независимым применением локальных правил.

Нужно явно отмечать:

- prerequisite rules;
- conflicting rules;
- rules that must be optimized jointly;
- rules that operate at sentence / paragraph / document level;
- rules that depend on genre, audience, author or context.

### 2.5. Разделять источник и проект

Нельзя выдавать современную инженерную формализацию за слова автора.

Каждый элемент должен иметь provenance.

## 3. Артефакты study

Рекомендуемый каталог:

```text
studies/<book-slug>/
  source.md
  coverage.md
  concepts.md
  rules.md
  interactions.md
  claims.md
  evals.json
  eval-map.json
  audit.md
```

Если проекту удобнее один большой файл, эти секции можно объединить. Но логическая структура должна сохраниться.

### `source.md`

Хранит:

- автор;
- название;
- язык;
- формат исходника;
- доступные библиографические данные;
- степень уверенности в издании;
- SHA-256 или другой fingerprint файла, если возможно;
- точное внутреннее оглавление;
- особенности пагинации;
- правила locators;
- copyright/source policy.

### `coverage.md`

Полная карта источника.

Для каждой главы/раздела:

- статус: `UNREAD / READ / EXTRACTED / VERIFIED`;
- есть ли новые operational ideas;
- сколько rules/concepts/claims извлечено;
- есть ли translation-only / historical / domain-specific material;
- есть ли unresolved questions;
- дата последней перепроверки.

Главная задача: не позволить системе заявить «книга разобрана», если часть глав фактически не проверена.

### `concepts.md`

Определения, категории, различия и модели, которые не являются прямыми правилами действия.

Например:

- что автор считает «ясностью»;
- чем отличаются два вида ошибок;
- как устроена авторская типология;
- что является единицей анализа.

### `rules.md`

Атомарные операционные правила.

Один rule должен отвечать на один диагностический вопрос.

### `interactions.md`

Связи правил:

- совместное применение;
- порядок;
- конфликты;
- приоритеты;
- compound failures;
- document-level effects.

### `claims.md`

Утверждения источника, которые не следует сразу превращать в правило.

Например:

- исторические факты;
- статистика;
- утверждения о языке/психологии/рынке;
- причинные объяснения;
- прогнозы;
- универсальные заявления.

Для каждого — статус внешней проверки.

### `evals.json`

Собственные тестовые случаи, не переписанные из книги.

Нужны:

- positive cases;
- negative cases;
- counterexamples;
- ambiguous cases;
- compound cases;
- context-dependent cases;
- preservation cases, где менять ничего не надо.

### `eval-map.json`

Трассировка:

`eval → rule/concept → source locator`.

### `audit.md`

Список того, что пока не доказано или не завершено:

- непрочитанные места;
- спорные интерпретации;
- возможные overgeneralizations;
- внешние источники, которые нужны для проверки;
- расхождения изданий;
- слабые evals;
- unresolved model behavior.

## 4. Карточка atomic rule

Для каждого правила хранить максимально однотипную структуру.

```markdown
## <RULE-ID> — короткое название

Source locator:
Scope:
Basis:
Level:
Confidence:

### Что проверяет

### Почему это важно

### Семантический/функциональный инвариант
Что нельзя потерять при исправлении.

### Trigger / признаки
Что должно заставить проверить правило.

### Диагностика
Какие вопросы задать тексту/ситуации.

### Возможные исправления
Не одна обязательная замена, а классы решений.

### Не применять автоматически
Контрпримеры и допустимые случаи.

### Do not infer
Каких более сильных выводов из правила делать нельзя.

### Взаимодействует с
Другие rule IDs.

### Positive example
Собственный пример проекта.

### Counterexample
Собственный пример, который похож снаружи, но не требует исправления.

### Verification
Как проверить, что после правки не стало хуже.
```

## 5. Таксономия provenance

Минимальный набор:

### `SOURCE_DIRECT`
Автор прямо формулирует принцип.

### `SOURCE_REPEATED`
Принцип не обязательно сформулирован одной фразой, но устойчиво проявляется в нескольких местах.

### `SOURCE_EXAMPLE_ONLY`
Есть пример, но обобщение может быть нашим.

### `PROJECT_DERIVED`
Проект выводит операционное правило из материала книги.

### `PROJECT_REFINED`
Исходная идея сохранена, но ограничена современными знаниями, контекстом или архитектурой проекта.

### `EXTERNAL_CONFIRMED`
Идея дополнительно подтверждена внешним нормативным, научным или эмпирическим источником.

### `EXTERNAL_CONTESTED`
Есть существенные основания считать утверждение спорным или устаревшим.

---

## 6. Таксономия scope

Framework не навязывает конкретные коды, но рекомендует хранить минимум следующие измерения отдельно:

### Область применимости

- general;
- genre-specific;
- audience-specific;
- translation-specific;
- spoken/written;
- professional/domain-specific;
- historical;
- author-specific.

### Уровень текста

- token/word;
- phrase;
- sentence;
- paragraph;
- scene;
- document;
- corpus/author profile.

### Severity / тип результата

Нельзя смешивать:

- factual/semantic error;
- formal/normative error;
- probable usage problem;
- style warning;
- author mismatch;
- optional improvement;
- unresolved question.

## 7. Процесс чтения

### Pass 0 — source inventory

До анализа:

1. определить файл и формат;
2. извлечь точное оглавление;
3. установить воспроизводимый locator;
4. зафиксировать библиографическую неопределённость;
5. посчитать fingerprint, если доступен исходный файл;
6. создать `coverage.md` со всеми разделами в статусе `UNREAD`.

### Pass 1 — sequential reading

Читать источник последовательно от начала до конца.

Нельзя заявлять full study, если анализ построен только на semantic search snippets.

Для каждой главы фиксировать:

- главную задачу;
- новые concepts;
- candidate rules;
- exceptions;
- positive models;
- examples that reveal boundaries;
- cross-references;
- claims for external verification.

После чтения глава становится `READ`, но ещё не `VERIFIED`.

### Pass 2 — atomic extraction

Разбить материал на минимальные различия, способные изменить решение.

Плохая атомизация:

`RULE-VOICE — голос должен быть естественным`.

Хорошая атомизация может разделить:

- возраст;
- социальную среду;
- эмоциональную ситуацию;
- эпоху;
- внутреннюю/внешнюю речь;
- профессиональный регистр.

Но нельзя дробить ради количества. Если два правила всегда диагностируются и исправляются одинаково, возможно, это одно правило.

### Pass 3 — counterexample extraction

Для каждого candidate rule найти в книге или вывести из её метода минимум один случай, где поверхностный trigger **не должен** вести к исправлению.

Если counterexample сформулировать невозможно, правило подозрительно похоже на слишком широкий запрет.

### Pass 4 — interaction pass

Перечитать rules не по главам, а по механизму.

Найти:

- дубликаты;
- contradictions;
- prerequisites;
- sequences;
- compound effects;
- случаи, когда исправление одного дефекта создаёт другой.

### Pass 5 — provenance audit

Для каждого rule проверить:

- действительно ли он есть в источнике;
- не оказался ли наш вывод сильнее исходного материала;
- не потеряли ли мы ограничения;
- не смешали ли разные главы в ложное универсальное правило.

### Pass 6 — external audit

Отдельно проверить утверждения, которые требуют внешней опоры:

- грамматическая норма;
- статистика;
- научный факт;
- исторический факт;
- современное употребление;
- психологическая причинность;
- правовое утверждение;
- техническая совместимость.

Сам автор книги не является достаточным доказательством для утверждений вне его области или эпохи.

### Pass 7 — eval construction

Создать оригинальные тесты.

Для каждого important rule желательно:

- один clear failure;
- один clear acceptable case;
- один tricky/context case;
- при необходимости compound case.

### Pass 8 — completeness audit

Book study нельзя считать полным, пока:

- каждая глава имеет статус `VERIFIED` или явно `NO_OPERATIONAL_CONTENT`;
- каждый rule имеет locator;
- каждое сильное утверждение имеет provenance;
- каждый contextual rule имеет counterexample;
- каждый rule покрыт хотя бы одним eval;
- important interactions покрыты compound evals;
- unresolved claims перечислены явно.

## 8. Проверка на потерю содержания

После первой версии выполнить специальный **loss audit**.

Для каждой главы спросить:

1. Какие различия автор проводит между похожими случаями?
2. Какие слова типа «но», «кроме», «иногда», «не всегда», «лишь если» меняют границы правила?
3. Какие примеры опровергают слишком простое резюме главы?
4. Есть ли положительный образец, который учит что-то сохранять?
5. Есть ли мета-правило о самом процессе мышления/редактирования?
6. Есть ли причина ошибки, а не только её внешний признак?
7. Есть ли interaction с идеей из другой главы?
8. Есть ли исторический контекст, без которого рекомендация исказится?
9. Есть ли термин/различие, которое мы ещё не формализовали?
10. Можно ли по нашей базе принять то же решение, что после чтения соответствующего места книги?

Если ответ на 10-й вопрос «нет», extraction неполон.

---

## 9. Проверка на избыточное воспроизведение источника

Особенно для охраняемых авторским правом книг.

В публичный study не включать:

- длинные цитаты;
- последовательные перефразы абзац за абзацем;
- полный набор авторских примеров;
- структуру, которая фактически заменяет чтение оригинала ради содержания/изложения автора.

Допустимая цель: создать **самостоятельную систему знаний и инструмент работы**.

Предпочитать:

- собственные формулировки;
- собственные примеры;
- ссылки на главы/секции;
- краткие цитаты только там, где точная формулировка сама является предметом анализа.

## 10. Quality gates

Рекомендуемые автоматические проверки:

### Structural

- все IDs уникальны;
- locators существуют;
- coverage содержит все главы;
- нет `UNREAD` при статусе complete;
- каждый rule есть в rule index;
- каждый rule имеет eval coverage;
- каждый contextual rule имеет counterexample;
- eval map не ссылается на неизвестные IDs;
- все claims имеют verification status.

### Semantic/manual

Автоматикой не заменить:

- faithful interpretation;
- отсутствие overgeneralization;
- качество counterexample;
- корректность современного переноса старого материала;
- сохранение авторского замысла;
- взаимодействие правил.

Для этого нужен отдельный human/model review.

---

## 11. Статусы завершённости study

### `INGESTED`
Источник доступен, оглавление и metadata зафиксированы.

### `READ`
Источник последовательно прочитан, но extraction ещё может быть грубым.

### `EXTRACTED`
Concepts/rules/claims извлечены по всему источнику.

### `TRACEABLE`
Все элементы имеют provenance и locators.

### `EVALUATED`
Созданы evals и counterexamples.

### `AUDITED`
Выполнены loss audit, overgeneralization audit и external claims audit.

### `OPERATIONAL`
Study можно использовать без исходника для обычной работы; исходник нужен только для спорных provenance-проверок или повторного исследования.

Нельзя ставить `OPERATIONAL`, если остаются неизвестные непрочитанные главы или rule без границ применимости.

---

## 12. Definition of Done

Полный book study считается готовым, когда:

1. весь источник последовательно просмотрен;
2. покрытие доказуемо по оглавлению;
3. все decision-relevant distinctions извлечены;
4. source vs project inference разделены;
5. правила атомарны, но не искусственно раздроблены;
6. contextual rules содержат counterexamples;
7. взаимодействия описаны;
8. внешне проверяемые claims не маскируются под правила;
9. evals покрывают rules и compound behavior;
10. выполнен отдельный loss audit;
11. выполнен отдельный overgeneralization audit;
12. публичные материалы не воспроизводят книгу в защищённой форме;
13. обычная работа возможна по study без постоянного доступа к исходнику;
14. при споре можно восстановить provenance до конкретного места источника.
