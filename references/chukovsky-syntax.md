# Чуковский: синтаксические операции, которые нельзя свести к regex

Этот файл появился после повторной проверки главы о канцелярите в «Живой как жизнь». Он фиксирует несколько рекомендаций, которые важны для `SKILL`, но опасны для поверхностного линтера без морфологического анализа.

## SYN-CHUK-01. Разрывать длинные цепи зависимых имён

Чуковский отдельно атакует цепочки родительных падежей: при большом числе вложенных зависимостей читателю приходится вручную восстанавливать дерево отношений.

### Не правило «не больше N родительных»

Количество падежных форм само по себе ничего не доказывает. Проблема начинается, когда:

- зависимость трудно восстановить;
- несколько существительных конкурируют за одну и ту же связь;
- предложение приходится перечитывать;
- иерархия отношений становится ясна только из внешнего знания.

### Положительная операция

1. Построить мысленное дерево зависимостей.
2. Выделить главное событие/утверждение.
3. Часть зависимостей превратить в придаточную конструкцию, отдельную клаузу, прилагательное или предложную группу.
4. Проверить, что новая версия выражает ту же иерархию.

Цель — не уменьшить число падежей, а **сделать структуру отношений видимой**.

## SYN-CHUK-02. Проверять творительный на конкурирующие роли

В сочетании номинализации, пассива и нескольких творительных одна форма может обозначать:

- деятеля;
- инструмент;
- новую роль/статус;
- характеристику.

Из-за одинакового падежного оформления возникает реальная синтаксическая двусмысленность.

### Положительная операция

Если в одном узле есть несколько творительных с разными семантическими ролями:

1. назвать деятеля подлежащим, если это не ломает фокус;
2. или превратить действие в активную клаузу;
3. или явным предлогом/порядком развести инструмент и деятеля;
4. затем проверить тему/рему — ясность не должна случайно менять смысловой акцент.

Это уже может быть не `STYLE_WARNING`, а `LANGUAGE_ERROR`/`SEMANTIC_ERROR`, если исходник действительно допускает конкурирующие разборы.

## SYN-CHUK-03. Номинальное отрицание распаковывать в условие/событие

Канцелярские цепочки типа `неполучение → нерассмотрение`, `наличие отсутствия`, `возникновение исчезновения` перегружают читателя абстрактными отрицаниями.

### Положительная операция

Попробовать восстановить событийную связь:

`если X не произойдёт → Y не произойдёт`

или другую фактическую связь, которую действительно задаёт исходник.

Это полезно не только для простоты: при распаковке становится легче увидеть, не перепутана ли причинность или полярность.

## SYN-CHUK-04. Plain-language backtranslation как semantic check

Чуковский показывает случаи, когда престижно-официальная оболочка затемняет настолько, что буквальное содержание расходится с намерением автора.

Для `humanizer+ru` из этого следует сильный метод:

1. взять сложную канцелярскую фразу;
2. **не редактировать её красиво**, а сначала пересказать самым простым русским языком;
3. сравнить получившуюся пропозицию с контекстом и заявленным намерением;
4. только затем строить чистовик.

Это аналог обратного перевода, но внутри одного языка.

### Почему это важно

Обычный stylistic pass может сделать ошибочную мысль гладкой. Plain-language backtranslation сначала проверяет **семантический каркас**.

Если возможны два разных пересказа, это сигнал синтаксической/семантической неоднозначности, а не повод выбрать понравившийся без основания.

## SYN-CHUK-05. Read-aloud pass должен проверять не только звук

В главе о канцелярите чтение вслух обнаруживает одновременно:

- нелепые созвучия;
- сбой ритма;
- слишком длинную зависимость;
- падежную связь, которая при чтении перестаёт быть прозрачной.

Поэтому `read aloud` в `SKILL` должен быть последним **синтаксико-просодическим** тестом, а не декоративной проверкой благозвучия.

## Почему этого пока нет в regex-linter

Надёжный детектор потребует как минимум:

- морфологического разбора;
- определения падежа и синтаксической головы;
- различения семантических ролей творительного;
- построения dependency tree;
- контекстного разрешения неоднозначности.

Regex по окончаниям дал бы слишком много ложных срабатываний и противоречил бы методологии самого проекта.

До появления такого слоя эти проверки выполняются моделью по `SKILL`/reference и покрываются eval-сценариями.
