# AGENTS.md — обязательный архитектурный контракт

Этот файл действует на весь репозиторий `humanizer_russian`.

Если ты работаешь как coding/research agent, **сначала следуй этому контракту**, затем читай только те reference/source-файлы, которые нужны для конкретной задачи. Не загружай весь knowledge/reference слой «на всякий случай».

## 1. Один проект

Каноническое имя проекта: **`humanizer_russian`**.

Нормативный русский, живой русский, редакторские школы, AI-эвристики и персонализация под автора — внутренние слои одного проекта. Не создавай отдельные продуктовые сущности вроде `humanizer+ru`, `humanizer+ru+user` и т. п.

## 2. Базовая иерархия

Жёсткие ограничения:

`USER_INTENT + SEMANTICS + NORM`

Выбор среди допустимых вариантов:

`AUTHOR > NATIVE_USAGE > EDITING > AI_CALQUE > detector score`

Смысл:

- `USER_INTENT` — не ломать задачу пользователя;
- `SEMANTICS` — не менять факты, референты, причинность, полярность и степень уверенности;
- `NORM` — не создавать настоящих ошибок русского языка;
- `AUTHOR` — при наличии корпуса учитывать подтверждённый идиолект;
- `NATIVE_USAGE` — среди правильных вариантов предпочитать естественный русский носителя;
- `EDITING` — Галь, Ильяхов, Чуковский и другие редакторские методы;
- `AI_CALQUE` — убирать машинные/англоязычные способы упаковки мысли;
- detector score — диагностический сигнал, не цель.

**Редакторская школа не имеет права отменять `NORM` или `NATIVE_USAGE` только потому, что книга рекомендует другую поверхность.**

## 3. Mechanical-first — обязательная архитектура runtime

Основной принцип:

> Что можно проверить надёжно и дёшево кодом — проверяется кодом. Контекстная модель подключается только там, где механика не может решить задачу без заметного риска ошибки.

Основной runtime:

```bash
python scripts/check.py text.md
```

Глубокий/исследовательский режим:

```bash
python scripts/check.py --extended text.md
```

Полный surface linter находится в `scripts/lint.py`.

Нельзя превращать основной runtime в «битву токенов», где модель каждый раз читает все книги, reference-файлы и длинные инструкции.

## 4. Уровни автоматизации

Каждую новую идею сначала отнеси к одному из уровней.

### A. HARD_GATE

Допустим только когда нарушение можно определить с очень высокой точностью и оно действительно блокирующее.

Типичные кандидаты:

- надёжный технический `ARTIFACT`;
- однозначная машинно-проверяемая ошибка нормы, если для неё есть достаточная база и исключения.

Книжная рекомендация, AI-маркер или вкусовая стилистика **не могут стать HARD_GATE сами по себе**.

### B. DEFAULT_MECHANICAL

Высокоточная surface-проверка, которую полезно показывать обычному пользователю без model reasoning.

Правило попадает сюда только после deterministic benchmark с отрицательными контролями.

Список default-правил контролируется `scripts/check.py` (`MECHANICAL_RULES`).

### C. EXTENDED_SOFT

Механическая эвристика с полезным recall, но заметным риском false positive.

Показывается только через `--extended` или при явном аудите. Не является приказом переписать текст.

### D. MODEL_ONLY

Зависит от смысла, дискурса, темы/ремы, референтов, жанра, просодии, идиомы, POV, авторского намерения или длинного контекста.

Не имитируй такую проверку regex-ом только ради «автоматизации».

### E. METRIC_ONLY

Описательная статистика без нормативного порога: длина предложений, частота частиц, распределение абзацев и т. п.

Метрика не превращается в ошибку без отдельной калибровки.

## 5. Классы правил не смешивать

Используй смысловую классификацию:

- `NORM-*` — подтверждённая норма русского языка;
- `NATIVE-*` — наблюдение/предпочтение живой речи носителей среди допустимых вариантов;
- `EDIT-*` — редакторская операция или рекомендация;
- `AI-CALQUE-*` — вероятностный машинный/переводной паттерн;
- `AUTHOR-*` — корпусно подтверждённый идиолект;
- `ARTIFACT-*` — технический след;
- source namespaces (`GAL-*`, `ILY-*`, `CHUK-*` и др.) — **provenance/source layer**, а не автоматическая severity.

Не называй native preference грамматической ошибкой. Не называй книжный совет нормой. Не называй нормальную русскую конструкцию AI-паттерном только потому, что она часто встречается у LLM.

## 6. Как добавлять mechanical rule

Новый mechanical rule нельзя просто дописать в regex и считать готовым.

Минимальный пакет:

1. **True positive** — конструкция, которую правило обязано найти.
2. **Natural negative control** — естественный русский с похожей поверхностью, который нельзя флагать.
3. **Boundary case** — пограничный пример.
4. **Intentional-use counterexample** — осознанный риторический/жанровый случай, если применимо.
5. **Exclusions** — code, URL, цитаты, markdown, диалог и другие зоны, если они создают false positives.
6. Regression case в `tests/lint_cases.json`.
7. Успешный `python scripts/benchmark_lint.py`.

Для продвижения в `DEFAULT_MECHANICAL` нужен прежде всего **precision**, а не максимальный recall.

Если правило не выдерживает отрицательные контроли, оставь его `EXTENDED_SOFT` или `MODEL_ONLY`.

## 7. Не подгонять benchmark под правило

При конфликте нового правила с существующим natural negative control сначала предполагай, что правило слишком широкое.

Нельзя молча менять/удалять negative tests, чтобы новая эвристика «стала зелёной».

Изменить ожидаемый результат теста можно только если сам тест признан неверным; это должно быть явно объяснено в PR.

## 8. Русский native layer — фундамент

Перед редакторскими школами сохраняй принципы уже принятого `NATIVE_USAGE`:

- контекстная экономия и безопасный эллипсис;
- не повторять общий материал без функции;
- сначала рассмотреть опущение/вынос/перестройку, потом синонимизацию;
- учитывать морфологию, падежи, управление и согласование;
- не держать русский в механическом SVO-lock;
- учитывать информационную структуру и сильные края фразы;
- русифицировать противопоставление, а не уничтожать его;
- различать функциональную парцелляцию и бессмысленную рубку;
- не удалять прагматические частицы механически;
- не портить пунктуацию ради detector score;
- не имитировать неграмотность ради «человечности».

Если рекомендация Галь/Ильяхова/Чуковского конфликтует с естественным русским, сначала проверь scope редакторской рекомендации. `EDITING` идёт после `NATIVE_USAGE`.

## 9. Reference-файлы — не runtime по умолчанию

`references/*`, `knowledge/*`, книжные source maps и длинные contextual notes — база знаний и разработки, а не обязательный prompt для каждой проверки.

Правило загрузки:

- сначала mechanical check;
- затем точечно открыть reference, который нужен для конкретной найденной проблемы;
- model-only слой подключать адресно;
- не читать все книги/правила для обычной surface-проверки.

Особенно `references/native-russian-user-context.md` — источник для разработки/проверки `NATIVE-*`, а не файл, который нужно каждый раз целиком отправлять модели.

## 10. Интеграция новых книжных/редакторских веток

При интеграции Галь, Ильяхова, Чуковского или нового источника **текущий `main` является архитектурной базой**.

Если source-ветка была создана до последних изменений `main`:

1. сначала синхронизируй её с текущим `main` или создай новую integration-ветку от `main`;
2. не разрешай конфликт простым выбором «theirs» для core-файлов;
3. переноси source-specific знания и проверки поверх текущей архитектуры;
4. сохраняй mechanical-first runtime, benchmark и selective context loading;
5. не возвращай старую detector-driven или context-heavy архитектуру через конфликт merge.

### Core-файлы, которые нельзя wholesale заменять старой версией из source-ветки

- `AGENTS.md`;
- `SKILL.md`;
- `scripts/check.py`;
- `scripts/lint.py`;
- `scripts/benchmark_lint.py`;
- `tests/lint_cases.json`;
- `.github/workflows/quality.yml`;
- `CONTRIBUTING.md`;
- `README.md`.

Их нужно **интегрировать**, а не откатывать.

## 11. Как подключать source-specific lint

Предпочтительная схема для крупных источников:

- отдельный модуль: например `scripts/lint_ilyakhov.py`, `scripts/chukovsky_checks.py`;
- главный `scripts/lint.py` агрегирует результаты;
- source-specific finding остаётся неблокирующим, пока не доказана другая severity;
- default checker показывает его только после отдельной калибровки;
- source-specific structural validator можно добавить в CI, но он дополняет, а не заменяет базовый benchmark.

Не раздувай один огромный regex-файл, если источник естественно выделяется в модуль.

## 12. Книги дают EDITING, не NORM автоматически

Для правил из книг:

- сохраняй provenance;
- указывай scope;
- отделяй прямое утверждение источника от project-derived вывода;
- ищи positive operation, а не только запрет;
- добавляй counterexamples;
- исторические и нормативные claims перепроверяй по актуальному authoritative source;
- не импортируй словарь/список автора как unconditional replacement map.

Книжная рекомендация может стать `NORM-*` только после отдельной современной нормативной верификации.

## 13. Model evals — вторичный контур

Model evals нужны для того, что нельзя честно проверить механически:

- сохранение смысла;
- голос;
- тема/рема;
- идиома;
- уместность регистра;
- POV;
- эмоциональный такт;
- сложное взаимодействие нескольких правил.

Они не заменяют deterministic benchmark для surface rules.

Не объявляй набор JSON-сценариев «пройденным benchmark», если модель фактически не запускалась.

## 14. Author profile

Персонализация — внутренний слой того же проекта.

Профиль строится по корпусу и может хранить:

- частотную лексику и частицы;
- n-граммы;
- sentence/paragraph distributions;
- code-switching;
- пунктуационные привычки;
- наблюдаемые stance markers;
- ручные annotations для локальной/поколенческой/профессиональной лексики.

Не выводи психологические диагнозы. Ошибки автора храни отдельно и по умолчанию не имитируй.

## 15. Definition of Done для изменения правил

Перед PR/merge выполни минимум:

```bash
python -m compileall -q scripts
python scripts/lint.py --self-test
python scripts/benchmark_lint.py
```

Если менялся author profiler — проверь schema validation.

Если добавлялись JSON fixtures — проверь parse/validator.

Если добавлялся source-specific validator — включи его в `.github/workflows/quality.yml`.

CI должен **добавлять** проверки, а не удалять базовые compile/self-test/benchmark checks.

## 16. Что писать в PR

PR, который добавляет языковой/редакторский слой, должен явно ответить:

1. Какой источник/provenance?
2. Какие новые правила/операции?
3. Какие из них mechanical, extended, model-only, metric-only?
4. Что является hard gate и почему?
5. Какие positive/negative/boundary tests добавлены?
6. Каков риск false positives?
7. Какие изменения runtime-контекста нужны? По умолчанию ответ должен быть «минимальные/адресные».
8. Не конфликтует ли слой с `NATIVE_USAGE`?
9. Что сознательно **не** автоматизировано?

## 17. Главное правило при сомнении

Если приходится выбирать между:

- ещё одним длинным prompt/reference-файлом;
- и маленькой воспроизводимой механической проверкой с хорошими negative controls,

предпочитай второе.

Если механическая проверка врёт без контекста — не усложняй regex до псевдолингвистики; оставь её model-only.

Цель проекта — **проверяемый русский редактор**, а не система, которая выигрывает за счёт объёма контекста.
